# Shopping Buddy — Change Log

## 2026-09-20 (meal plans persisted)
### Roadmap Phase A, step 10: persist meal plans
- Corrected a documentation/reality mismatch found while starting this: `docs/01_CURRENT_STATE.md` claimed meal-plan recipes were "seeded into Neon" — verified this was never true. There is no `recipes` table in `lib/db/schema.ts`, and `lib/db/seed.ts` never seeds the `meal_plans` table either. The recipe catalog (`RECIPES` in `lib/meal-plans.ts`) was always code-based reference data, not a DB table; only the (empty, unused) `meal_plans` table — meant to store a household's *generated* weekly plan, not the catalog — existed.
- Fixed a real bug uncovered while wiring this up: `components/dashboard/meal-plan.tsx` generated plans against a hardcoded mock household (`initialHousehold` from `lib/mock-data.ts`) instead of the signed-in household, so allergen filtering was silently checking the wrong family's allergies for every real user. Now takes the real `household` as a prop.
- Added `saveMealPlanAction` (`app/actions/meal-plan.ts`): upserts one `meal_plans` row per household per week (found via `household_id` + `week_start`, updated in place on repeat generation rather than accumulating duplicate rows for the same week). Recipe generation itself (`generateWeeklyPlan`) stays a pure client-side calculation over real server-fetched household data, matching the existing pattern — only the resulting plan is persisted.
- Added `currentWeekStart()` to `lib/meal-plans.ts` and a read path in `lib/db/queries.ts` (`getHouseholdData` now also returns `mealPlan: SavedMealPlan | null`) so a previously generated plan survives a page reload instead of resetting to blank.
- **Bug caught and fixed during verification, not just build/typecheck**: the first version of `currentWeekStart()` mixed local-timezone `Date` methods (`getDay`/`setDate`) with UTC-based `toISOString()`. On this machine (Europe/Prague, UTC+2) that silently computed the wrong Monday (one day off) — a direct DB round-trip test caught it before it shipped. Rewritten with pure UTC calendar math (`Date.UTC` + `getUTCDay`/`setUTCDate`) so the result no longer depends on server timezone, which matters since dev machines and Vercel's runtime won't generally share one.
- Verified end-to-end against the real database: a saved plan is null before generating, an inserted plan round-trips back through `getHouseholdData` with the correct week (2026-09-14, the Monday of the week containing the app's `TODAY`), budget, and all 7 days intact; a real sign-up + page load renders the meal-plan section without errors.

## 2026-09-20 (stores, prices, deals persisted)
### Roadmap Phase A, steps 8–9: normalize stores, persist prices/deals
- Added `pricesRelations` and `dealsRelations` to `lib/db/schema.ts` — the tables and FK columns already existed, but Drizzle's relational query API (`db.query.x.findMany({ with: {...} })`) needs an explicit `relations()` export per table to traverse it; `prices`/`deals` had FK columns but no relations, so they couldn't be joined via `with` yet.
- Added `getStores()` and `getProductPrices()` to `lib/db/queries.ts`. `getStores()` returns every store location with its active-deal count and available-products list derived from real `prices`/`deals` rows (not a hand-maintained list). `getProductPrices()` returns each product's latest recorded price per store, with any currently-active deal folded in.
- `lib/prices.ts` is now a pure calculation module (`effectivePrice`, `isDealActive`, `comparePrices`, `activeDeals`) operating on data passed in, not a mock-data file — matches `docs/02_ARCHITECTURE.md`'s `lib/domain/`-style separation. The `PRODUCT_PRICES` fixture array moved to `lib/mock-data.ts` (it's seed data, not domain logic) and `lib/db/seed.ts` was updated to import it from there.
- Dropped `priceRangeLast3Months` / the "min–max over 3 months" stat: the seeded data has exactly one price snapshot per product/store (no real historical rows yet, see gap 8), so a "3 month range" computed from a single point would show a fake-looking flat range instead of reflecting reality. Revisit once real price updates accumulate over time.
- Rewired `components/stores/store-directory.tsx`, `components/dashboard/price-watch.tsx`, `components/shopping/price-comparison.tsx`, and `components/shopping/shopping-list.tsx` to receive `stores`/`productPrices` as props (fetched in `app/page.tsx` alongside household data) instead of importing `lib/mock-data.ts`/`lib/prices.ts` directly. Added an empty state to `PriceWatch` for when there are no active deals. Fixed `shopping-list.tsx`'s hardcoded preferred-store list, which was missing Penny and JIP.
- Verified against the real database (not just build/typecheck): `getStores()`/`getProductPrices()` called directly return the 6 seeded stores and 4 seeded products with correct joined deal/price data; a fresh sign-up + page load renders the real active deals (Mléko polotučné/Lidl, Kuřecí prsa/Albert, Toaletní papír/Kaufland with their real discount dates) in the UI.
- Store directory and price/deal history remain the next items from the `docs/01_CURRENT_STATE.md` gap list: normalization beyond chain+location (product/brand/variant/package/unit) and actual price history over time are still open.

## 2026-09-20 (household authorization)
### Added: server-side ownership checks on every Server Action
- Closed the gap noted in the previous entry: `app/actions/{household,shopping,budget,notifications}.ts` previously trusted whatever id (household, member, child, list, item, notification) the client passed, with no check that it belonged to the caller. Any signed-in user could have read/written another household's data by passing its id — a classic IDOR gap, now that sessions exist to check against.
- Added `lib/auth/authorize.ts` — `requireHouseholdId()` resolves the caller's household from their session (`auth.getSession()` → `household_members.user_id`) and throws `ForbiddenError` if there's no session or no household, instead of trusting a client-supplied id.
- Actions that create/list top-level household data (`updateHouseholdAction`, `addHouseholdMemberAction`, `addChildAction`, `updateHouseholdPreferencesAction`, `addShoppingListAction`, `addExpenseAction`, `markAllNotificationsReadAction`) no longer take a `householdId` parameter at all — it's derived server-side, so there's nothing for a client to forge. Updated call sites in `components/app-shell.tsx` to match.
- Actions that act on a specific row the client must still identify by id (`removeHouseholdMemberAction`, `removeChildAction`, `addShoppingItemAction`, `updateShoppingItemAction`, `toggleShoppingItemAction`, `removeShoppingItemAction`, `markNotificationReadAction`) now look up that row first and verify it belongs to the caller's household before mutating it, throwing otherwise.
- Not yet end-to-end tested for the same reason as the previous entry (`NEON_AUTH_BASE_URL` placeholder) — verified via `tsc --noEmit` and `next build`, and by re-reading each action against its call site.

## 2026-09-20 (authentication foundation)
### Added: Neon Auth (Managed Better Auth) integration
- Per `docs/03_DATABASE.md`'s instruction to inspect `neon_auth` before building a separate auth system: inspected it directly (`information_schema` + `neon_auth.project_config`) and found the full Managed Better Auth schema already provisioned (`user`, `session`, `account`, `organization`, `member`, `invitation`, `jwks`, `project_config`) but with zero rows in every identity table — the service was provisioned but never wired up. Decided to use it rather than the placeholder local `users` table, which had no real login behind it.
- **Schema migration** (`lib/db/migrations/0001_neon_auth_integration.sql`, applied via a new minimal runner at `lib/db/migrate.ts` / `pnpm db:migrate`): dropped `public.users`; `household_members.user_id` now has an FK to `neon_auth."user"(id)` (`ON DELETE SET NULL`) instead. The two pre-existing demo `household_members` rows (Lucie/Petr fixtures) had their `user_id` cleared first since they were never linked to a real login — no real account data existed to lose. This is a hand-written SQL migration, not a `drizzle-kit generate` one — the previous `drizzle-kit push`-only workflow has no migration history to build on, and `neon_auth` is managed by Neon directly so it's deliberately not declared in `lib/db/schema.ts`. Adopting `drizzle-kit generate`/`migrate` end-to-end remains open (see `docs/01_CURRENT_STATE.md` gap list).
- **App wiring**: `@neondatabase/auth` (email/password, per product decision — Google/social and magic-link were considered and deferred) with `lib/auth/server.ts` (`createNeonAuth`), `lib/auth/client.ts`, the catch-all route `app/api/auth/[...path]/route.ts`, and `proxy.ts` (Next.js 16's middleware successor) protecting every route except `/api/auth`, `/auth/*`, and static assets. Added `app/auth/sign-in` and `app/auth/sign-up` pages.
- **Per-user household scoping**: `getHouseholdData()` in `lib/db/queries.ts` now takes `(userId, userName)`, resolves the caller's household via `household_members.user_id`, and auto-provisions a fresh empty household (owner member + default preferences + a starter shopping list) on a user's first login — per product decision, new users do **not** inherit the existing seeded demo household; that household still exists in the database (untouched, just no longer linked to any account) rather than being deleted. `app/page.tsx` now requires a session (redirects to `/auth/sign-in` otherwise) and passes the real user's name down through `AppShell`/`AppHeader`, replacing the previously hardcoded "Lucie" greeting and "LK" avatar initials — those were about to be visibly wrong for the first non-demo user. Added a working sign-out control in `AppHeader`.
- `lib/db/seed.ts` updated to match (no more `schema.users` inserts; demo `household_members` rows are seeded without a `user_id`).
- **Known blocker, not yet resolved**: `NEON_AUTH_BASE_URL` and `VITE_NEON_AUTH_URL` in `.env.local` are still the literal placeholder value `"provisioning"`, not a real endpoint — the Neon Auth service's schema/config exists but env vars were pulled before it finished activating. Verified the code path is otherwise correct: build/typecheck are clean, the proxy correctly redirects unauthenticated requests, and `/auth/sign-in` renders; only the actual `POST /api/auth/sign-up/email` call fails (500, not a crash) because the base URL can't be reached. Needs a fresh env pull (Vercel/Neon dashboard, or `vercel env pull` / `neon env pull` once a CLI is authenticated) before sign-up/sign-in can work end-to-end.
- Household/user authorization scoping of the write-side Server Actions (`app/actions/*` still trust whatever id is passed in, not yet checking it belongs to the caller's household) is the next gap this unblocks — tracked as follow-up, not done here.
