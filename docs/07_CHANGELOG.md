## 2026-09-24 (Fix: a retailer's SKUs merged into one product by name)
### Product identity — found in the first real ingestion; stacked on the old-price UI PR (#27)
- **Bug:** the resolver attached a new SKU to any same-named catalog product, and `products.name` is unique, so several SKUs of one retailer that share a name became ONE product (8 products, 12 extra SKUs: Penny flavours of Raw tyčinka Crip Crop / Tyčinka Corny Big / Pribináček; Lidl sizes of olivový olej, kuřecí prsní řízky, rýže, mléko 1,5 %/3,5 %). Prices were mixed and promotions overwrote each other (35 Penny offers → 29 deals).
- **Fix:** `resolveProductForSku()` never reuses a product already linked to a different SKU of the same source; the SKU gets its own product "<name> (<SKU>)". Cross-store linking by name is unchanged (Billa + Penny "Okurka salátová").
- **Repair applied to the shared database:** `pnpm db:split-collapsed-products` (dry-run by default). +12 products, refs and official price rows unchanged in number, prices moved with their SKU, nothing deleted, re-run is a no-op. Active deals were left for the next ingestion run to re-upsert per SKU.
- **Tests:** 6 unit tests for the resolution rules; 4 DB-backed tests (SKUs kept apart across runs and without a shared context, cross-store link preserved, the repair incl. dry-run, price move and idempotency). The regression tests were confirmed to fail without the fix.

## 2026-09-24 (Price ingestion: run time brought under the function limit)
### Performance / reliability of `/api/cron/ingest-prices` — stacked on the DM PR (#25)
- **Cause (measured):** ~1 database round trip per query, ~10 queries per new product (incl. a full-catalog join and a duplicated ref lookup per product) → ~190 s for three stores, ~270 s with Lidl, against a 300 s limit with no `maxDuration`.
- **Fewer queries:** `loadExternalProductContext()` once per run, `touchExternalRefs()` once per run. Benchmark (40 synthetic products, cleaned up): new 39.1 s → 14.9 s, existing 19.4 s → 5.5 s.
- **Time budget:** `ingestPrices()`/connectors take a `deadline`; a run ends cleanly between products with `truncated: true`. `runPriceSources()` shares one 230 s budget, skips a source that would start too late and isolates failures. `maxDuration = 300` on the routes.
- **Request timeouts:** every connector request has a 20 s timeout (`lib/ingestion/http.ts`); DM stops after 5 consecutive failed lookups.
- **One cron per store:** `/api/cron/ingest-prices/<source>` (lidl 05:00, billa 05:10, penny 05:20, dm 05:30 in `vercel.json`); the bare route still runs all stores for manual runs; unknown source → 400. Dynamic path, not a query string, per Vercel's cron documentation.
- **Incident, fixed:** a local smoke test request without `CRON_SECRET` set ran a real Billa ingestion against the shared database and added 77 identical duplicate price rows; verified identical, then deleted (Billa is back to 77 rows).
- **Tests:** 28 new (orchestrator budget/deadline/context, `runPriceSources`, request timeout, connector deadlines, DM circuit breaker, cron handler status codes) plus 4 DB-backed tests for the new query helpers; CI-equivalent suite 407/407, `tsc` and `next build` clean.

Invalid JSON still throws. No database migration needed; stored rows are upgraded on read and rewritten in the new shape the next time the plan is saved.
- Tests: 11 new in `lib/meal-plans.test.ts` (reproduction of the original crash, `convertQuantity`/`matchIngredientToStock` with missing units, legacy upgrade equals a freshly generated plan, stock logic works on the upgraded plan, cooked meals/name/price preserved, current-shape plan unchanged, `null` cases, corrupt JSON throws). ## 2026-09-23 (Azure fallback now receives the cleaned-up photo too)
- The Azure Document Intelligence fallback previously got the untouched original (chosen so it would stay an independent second attempt). It now receives exactly what Google Vision gets: the cleaned-up copy, or the original when preparation fails or for a PDF. Rationale (owner's request): while Vision is unusable (billing disabled) Azure is the only working provider, and the clean-up is what improves its input. Trade-off: the fallback is no longer an independent attempt on different bytes, so a defect *caused by* the clean-up would hit both providers — mitigated because preparation failure already falls back to the original for both, and the clean-up steps are conservative (conditional lighting/deskew, no binarization or sharpening).
- Tests: replaced the "Azure gets the original" test with "same cleaned-up image as the primary" and added "both get the original when preparation fails".

- **Image preparation (`lib/receipt-image.ts`, new dependency `sharp` 0.35.3):** before OCR the photo is auto-rotated by EXIF, converted to grayscale, capped at 4000 px, lighting-flattened *only when uneven*, contrast-stretched, and straightened if clearly tilted, then sent as a grayscale JPEG. The original in Blob is never changed; preparation failure falls back to the original; PDFs are untouched; the Azure fallback initially got the original (superseded by the entry above). `sharp` was already installed transitively by Next at the same version, so this adds no new package to the tree (lockfile change: 3 lines). ~0.6 s and ~150 MB for a 12 MP photo.
- **Measured, not assumed.** Google Vision could not be used for measurement (see below), so an independent engine (Tesseract, installed outside the repo) scored 8 synthetic degraded copies of a Czech receipt (faded print, strong shadow, tilt 8°/−12°, shadow+tilt, low resolution, blur, sideways EXIF): mean text similarity **0.58 → 0.80**, share of price amounts found **68 % → 90 %**; shadow 0.33 → 0.81, sideways 0.15 → 0.78, tilt −12° amounts 50 % → 100 %; low-res and blurry unchanged (±0.01). Two variants tried were rejected on evidence: CLAHE barely flattened a smooth shadow, and *unconditional* flat-field cut the price amounts found on low-res photos from 83 % to 42 % — hence the lighting step is conditional on a measured unevenness (0.25–0.31 with a shadow, ≥ 0.71 otherwise; threshold 0.6). **Caveat:** synthetic degradations and a different engine — real gains on real receipts with Vision are unmeasured, and Vision is a stronger engine that tolerates some of these defects itself, so expect smaller gains than Tesseract showed.
- **File type from bytes (security):** upload previously trusted the client's MIME type against an allowlist; it now detects JPEG/PNG/WebP/PDF from magic bytes and ignores the declared type and file name (a PNG sent as `image/jpeg` is stored as `.png`; HTML or an executable claiming to be an image is rejected before anything is stored). Decoding refuses images above 80 megapixels (decompression bombs). Output is kept under 6 MB so the request fits Vision's 10 MB limit — a raw 10 MB upload would have exceeded it after base64.
- **HEIC:** was accepted at upload but could never be read (Vision does not accept it and `sharp`'s prebuilt binary decodes only AVIF). It is now rejected with an instruction (iPhone: Nejkompatibilnější), a stored HEIC ends in `ocr_failed` with that message instead of a raw API error, and the picker no longer lists `image/heic` so iOS converts to JPEG by itself.
- Import log gained `imagePrep` (status, ms, steps applied, output size, failure note).

## 2026-09-23 (Receipt discounts are now applied, validated and stored)
- **Gap closed:** the parser extracted `discount`/`discountTotal`, but `toReceiptLineItems` ignored them, so an imported purchase's total was the pre-discount sum (not what was paid) and `purchases.discount` (already in the schema and shown as "sleva X Kč" in the history) was never set by receipts. No migration was needed.
- **Semantics, now stated in the structuring prompt and enforced in code:** a line's `totalPrice` is pre-discount; `discount` is the positive amount off that line; `discountTotal` is *all* discounts (per-line plus receipt-wide such as coupons); `total` is the amount paid. Discounts are never their own items.
- **Stored result:** `purchase_items.price` = net per-unit price paid; `purchases.total` = paid (line totals net of their discounts, minus any receipt-wide discount no line carries); `purchases.discount` = amount saved. `ReceiptLineItem` gained an optional `discount` (whole-line amount) and keeps `price` pre-discount.
- **Price observations keep the pre-discount shelf price** as `regularPrice`: a receipt discount may be a personal coupon, not a shelf promotion, so recording the discounted amount would understate the product's regular price (CLAUDE.md section 18).
- **New review triggers (`hasInvalidAmounts`):** any negative price/discount, a discount larger than its line, or a discount emitted as its own negative "item". `isReceiptConsistent` now falls back to line discounts when there is no `discountTotal`, and treats line discounts exceeding a stated `discountTotal` as a contradiction. The review form shows an editable "Sleva" field on rows that carry one; confirming rejects a negative discount or one larger than the line.
- **Not done — VAT (DPH):** deliberately skipped. It would need a new column and nothing consumes it yet; add it when a feature (e.g. VAT-aware spending) needs it.
- Tests: `lib/receipts.test.ts` and `app/actions/receipts.test.ts` (line discount, coupon-only, no discount, negative-item discount routed to review, price observation stays pre-discount, reviewed discount not double-counted, invalid reviewed discounts rejected) — 100/100 in those two files, `tsc --noEmit` clean. - Per `docs/03_DATABASE.md`'s instruction to inspect `neon_auth` before building a separate auth system: inspected it directly (`information_schema` + `neon_auth.project_config`) and found the full Managed Better Auth schema already provisioned (`user`, `session`, `account`, `organization`, `member`, `invitation`, `jwks`, `project_config`) but with zero rows in every identity table — the service was provisioned but never wired up. Decided to use it rather than the placeholder local `users` table, which had no real login behind it.
- **Schema migration** (`lib/db/migrations/0001_neon_auth_integration.sql`, applied via a new minimal runner at `lib/db/migrate.ts` / `pnpm db:migrate`): dropped `public.users`; `household_members.user_id` now has an FK to `neon_auth."user"(id)` (`ON DELETE SET NULL`) instead. The two pre-existing demo `household_members` rows (Lucie/Petr fixtures) had their `user_id` cleared first since they were never linked to a real login — no real account data existed to lose. This is a hand-written SQL migration, not a `drizzle-kit generate` one — the previous `drizzle-kit push`-only workflow has no migration history to build on, and `neon_auth` is managed by Neon directly so it's deliberately not declared in `lib/db/schema.ts`. Adopting `drizzle-kit generate`/`migrate` end-to-end remains open (see `docs/01_CURRENT_STATE.md` gap list).
- **App wiring**: `@neondatabase/auth` (email/password, per product decision — Google/social and magic-link were considered and deferred) with `lib/auth/server.ts` (`createNeonAuth`), `lib/auth/client.ts`, the catch-all route `app/api/auth/[...path]/route.ts`, and `proxy.ts` (Next.js 16's middleware successor) protecting every route except `/api/auth`, `/auth/*`, and static assets. Added `app/auth/sign-in` and `app/auth/sign-up` pages.
- **Per-user household scoping**: `getHouseholdData()` in `lib/db/queries.ts` now takes `(userId, userName)`, resolves the caller's household via `household_members.user_id`, and auto-provisions a fresh empty household (owner member + default preferences + a starter shopping list) on a user's first login — per product decision, new users do **not** inherit the existing seeded demo household; that household still exists in the database (untouched, just no longer linked to any account) rather than being deleted. `app/page.tsx` now requires a session (redirects to `/auth/sign-in` otherwise) and passes the real user's name down through `AppShell`/`AppHeader`, replacing the previously hardcoded "Lucie" greeting and "LK" avatar initials — those were about to be visibly wrong for the first non-demo user. Added a working sign-out control in `AppHeader`.
- `lib/db/seed.ts` updated to match (no more `schema.users` inserts; demo `household_members` rows are seeded without a `user_id`).
- **Known blocker, not yet resolved**: `NEON_AUTH_BASE_URL` and `VITE_NEON_AUTH_URL` in `.env.local` are still the literal placeholder value `"provisioning"`, not a real endpoint — the Neon Auth service's schema/config exists but env vars were pulled before it finished activating. Verified the code path is otherwise correct: build/typecheck are clean, the proxy correctly redirects unauthenticated requests, and `/auth/sign-in` renders; only the actual `POST /api/auth/sign-up/email` call fails (500, not a crash) because the base URL can't be reached. Needs a fresh env pull (Vercel/Neon dashboard, or `vercel env pull` / `neon env pull` once a CLI is authenticated) before sign-up/sign-in can work end-to-end.
- Household/user authorization scoping of the write-side Server Actions (`app/actions/*` still trust whatever id is passed in, not yet checking it belongs to the caller's household) is the next gap this unblocks — tracked as follow-up, not done here.
