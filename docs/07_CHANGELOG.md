## 2026-09-22 (Real browser verification: Playwright added, two real bugs found and fixed)
### Follow-up to the previous entry, whose UI was only type-checked/built/unit-tested — no browser was available in that session
- Added `@playwright/test` as a dev dependency (via `npx pnpm add -D`, since `pnpm`/`corepack` weren't globally set up in this environment — used `npx pnpm@12.3.4` and `npx playwright install chromium` instead) so a real headless Chromium session can drive the app end to end from within this same session, without any external browser connector.
- Ran a full scripted walkthrough against the real dev server and real dev database: signed up a disposable test account, added and bought a shopping-list item, moved a pantry item between locations, generated a stock-aware meal plan, regenerated one meal, marked a meal cooked, and imported a receipt. This surfaced two real bugs neither `tsc` nor the test suite could catch, since both are about client-runtime behavior against a live server — see docs/01_CURRENT_STATE.md section 33 for full detail. In short:
  1. `addIngredients()` (`components/app-shell.tsx`) fired one `addShoppingItemAction` per ingredient *concurrently* via `Promise.all`. Every write actually succeeded, but a dozen-plus concurrent Server Actions each independently revalidating could apply a stale mid-batch snapshot over the correct optimistic state, leaving the shopping list looking empty until a hard reload. Fixed by awaiting each add sequentially. This bug pre-dated this session's meal-plan work but went from rare to routine once "Přidat chybějící do nákupního seznamu" started routinely generating 20-30-item batches.
  2. `getProductCatalog()` never returned a matched product's real category, so `addShoppingItemAction` always fell back to the schema default (`'Ostatní'`) for anything typed via the plain quick-add input — which meant `inferPantryLocation()`'s category-based branching almost never saw a real `'Potraviny'` item, so the fridge/freezer keyword heuristic rarely got to run in practice. Fixed by having `getProductCatalog()` also return each product's category and using it as the default when no explicit override is given.
- Both fixes covered by new/updated tests (`app/actions/shopping.test.ts`: matched-category default + explicit-override-wins; `lib/products.test.ts`: updated fixtures) plus a second round of browser re-verification confirming both are actually fixed (bulk add now shows correctly without a reload; "Kuřecí prsa" now correctly lands in Lednice instead of Spíž).
- Noted, not fixed: two genuinely different slow operations started back-to-back can still race the same way, since every Server Action here does its own independent `revalidatePath()` with no app-wide serialization. Judged out of scope for this fix per the smallest-coherent-change principle — documented as a known limitation instead of silently left undiscovered.

## 2026-09-20 (household authorization)
### Added: server-side ownership checks on every Server Action
- Closed the gap noted in the previous entry: `app/actions/{household,shopping,budget,notifications}.ts` previously trusted whatever id (household, member, child, list, item, notification) the client passed, with no check that it belonged to the caller. Any signed-in user could have read/written another household's data by passing its id — a classic IDOR gap, now that sessions exist to check against.
- Added `lib/auth/authorize.ts` — `requireHouseholdId()` resolves the caller's household from their session (`auth.getSession()` → `household_members.user_id`) and throws `ForbiddenError` if there's no session or no household, instead of trusting a client-supplied id.

Updated call sites in `components/app-shell.tsx` to match.
- Actions that act on a specific row the client must still identify by id (`removeHouseholdMemberAction`, `removeChildAction`, `addShoppingItemAction`, `updateShoppingItemAction`, `toggleShoppingItemAction`, `removeShoppingItemAction`, `markNotificationReadAction`) now look up that row first and verify it belongs to the caller's household before mutating it, throwing otherwise.
