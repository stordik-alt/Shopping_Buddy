## 2026-09-21 (shared household — invitations/membership)
### Roadmap Phase B, first item: invitations/membership
- Considered using Neon Auth's `organization`/`member`/`invitation` plugin (already provisioned in `neon_auth`, per the earlier auth work) instead of building this ourselves, per the project's stated preference for reusing Neon Auth over duplicating it. Decided against it here: the plugin's `organization` row carries none of this app's household-domain fields (budget, preferences, shopping lists, etc.), so `households` would still be needed regardless — using the plugin would mean keeping two membership records in sync (`neon_auth.member` and our own `household_members`) for no functional gain. - **Schema**: new `invitations` table (`lib/db/migrations/0002_invitations.sql`, applied via `lib/db/migrate.ts`) — token-based, not emailed automatically (no email-sending integration is provisioned yet). The household owner generates a share link and sends it themselves.

- **Auto-join on first login**: extended `getHouseholdData()` (now takes `userEmail` too) so that when someone with *no* household yet signs in and has a pending invitation matching their email, they join that household as a member instead of getting a fresh auto-provisioned one. - **Explicit accept flow**: new public page `/invite/[token]` (added to `proxy.ts`'s unauthenticated allow-list alongside `/auth/*`) handles the case where someone already has a session (or already belongs to a household) when they open the link — shows the household name and inviter, routes to sign-up/sign-in with the invited email prefilled (`?invite=&email=`), or shows a clear error for a mismatched email or existing membership. - Verified end-to-end against the real database: owner signs up → invites an email → a second account signing up with that exact email automatically lands in the owner's household as a member (not a new one), with the invitation flipped to `accepted`; an unrelated third signup is unaffected and still gets its own household. ## 2026-09-20 (household authorization)
### Added: server-side ownership checks on every Server Action
- Closed the gap noted in the previous entry: `app/actions/{household,shopping,budget,notifications}.ts` previously trusted whatever id (household, member, child, list, item, notification) the client passed, with no check that it belonged to the caller. Any signed-in user could have read/written another household's data by passing its id — a classic IDOR gap, now that sessions exist to check against.
- Added `lib/auth/authorize.ts` — `requireHouseholdId()` resolves the caller's household from their session (`auth.getSession()` → `household_members.user_id`) and throws `ForbiddenError` if there's no session or no household, instead of trusting a client-supplied id.
- Actions that create/list top-level household data (`updateHouseholdAction`, `addHouseholdMemberAction`, `addChildAction`, `updateHouseholdPreferencesAction`, `addShoppingListAction`, `addExpenseAction`, `markAllNotificationsReadAction`) no longer take a `householdId` parameter at all — it's derived server-side, so there's nothing for a client to forge. Updated call sites in `components/app-shell.tsx` to match.
- Actions that act on a specific row the client must still identify by id (`removeHouseholdMemberAction`, `removeChildAction`, `addShoppingItemAction`, `updateShoppingItemAction`, `toggleShoppingItemAction`, `removeShoppingItemAction`, `markNotificationReadAction`) now look up that row first and verify it belongs to the caller's household before mutating it, throwing otherwise.
- Not yet end-to-end tested for the same reason as the previous entry (`NEON_AUTH_BASE_URL` placeholder) — verified via `tsc --noEmit` and `next build`, and by re-reading each action against its call site.
